- **Single-tenant platform with Colombia focus (COP currency, NIT tax ID, Wompi payments)** (high) -> New features should assume Colombian market context; currency/tax handling is COP-specific; NIT validation may be required for suppliers
- **Multi-role user model with role-based workflows** (high) -> Users can hold multiple roles (home_owner, service_provider, seller); a supplier role would be additive via userRoles junction
- **Status-driven workflows with enumerated states** (high) -> Entities use pgEnum for status (serviceProviderStatusEnum, projectStatusEnum, agreementStatusEnum, sellerStatusEnum); new catalogue would likely need similar activation/approval states
- **Soft-delete pattern via isArchived boolean** (high) -> Projects and bids use isArchived for soft-delete; new catalogue entities should follow same pattern
- **isActive pattern for catalog/reference data** (high) -> Reference tables (services, specializations, designStyles, roomMaterialOptions) use isActive boolean for soft-disable; supplier catalogue would follow this pattern
- **Existing material catalog is room-scoped and project-bound** (high) -> roomMaterialOptions defines material choices per renovation area; NOT linked to suppliers/providers - it is a product selection catalog, not a supplier inventory system
- **Translation support via entity_translations polymorphic table** (high) -> i18n is supported via entityTranslations table keyed by entityType+entityId+langCode; catalogue items could leverage this pattern
- **Partner tier model (basic/premium/enterprise)** (medium) -> Partners have tiered access; if suppliers become partners or have tiers, similar enum pattern exists
- **Onboarding workflow tracking via step counters** (high) -> serviceProviders and sellers have profileSetupStep/onboardingStep integers; new supplier onboarding would follow same pattern
- **No explicit Market/Region scoping beyond country field** (medium) -> Users have a country field and legalDocuments are scoped by country code, but there is no marketplace regional partitioning; the platform appears to be a single-market (Colombia) system
- **Junction tables for many-to-many relationships follow consistent pattern** (high) -> serviceProviderToServices, serviceProviderToSpecializations, projectRoomMaterials use composite primary keys or separate id; new supplier-material links would follow same pattern
